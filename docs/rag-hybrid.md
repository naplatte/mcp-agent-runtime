# 向量＋关键词倒排检索

保留普通向量检索作为默认基准，通过 `--selection hybrid` 开启混合检索。
最终仍最多给模型 K 个工具，不增加查询 Embedding 或拆分模型请求。

## 过程

1. 向量一路：复用原问题向量，按余弦相似度取前50个。
2. 关键词一路：查询本地倒排索引，按 BM25 取前50个。
3. 合并去重：每个工具的融合分数是两路 `1 / (60 + 排名)` 之和，按融合分数选前 K 个。

BM25 使用 `k1=1.2、b=0.75`。融合常数60和最终工具数量 `--k 20` 是两个参数。
不直接相加余弦和 BM25 分数，因为它们的数值尺度不同。
算法说明参考 [RRF 官方文档](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)。

## 索引和语言处理

- 索引工具名、功能说明及参数名/参数说明，与向量编码使用相同元数据。
- 英文转小写；保留完整标识，同时拆分下划线、连字符和 camelCase。
- 中文按 UTF-8 字符生成单字和相邻双字，避免引入分词服务。
- 查询侧有一小组公开的通用词语对应，例如“邮件→email/mail”“目录→directory”“日程→calendar/event”。
  它们只作用于关键词查询，不改工具描述和向量，不使用评测答案，也不绑定题号或工具名。
- 添加、覆盖、删除、刷新工具时同步维护倒排；加载向量索引时从元数据重建，不增加 Embedding 请求。
- 只允许有效向量对应的工具参与融合。关键词无命中时沿用普通向量顺序。

通用词语对应还不等于完整跨语言理解。`page-7f21`、邮箱、issue 编号等参数值如果不在
工具元数据中，不会自动命中某个工具；倒排也不负责识别一段话里有几个需求。

## 运行

先只测检索，自动同时给出普通向量的工具找齐率：

```bash
python3 tests/rag_effectiveness/run.py --retrieval-only --selection hybrid --k 20
```

再对照“全量工具”和“混合RAG选20个工具”的模型选择效果：

```bash
python3 tests/rag_effectiveness/run.py --live --selection hybrid --k 20 --repeats 1
```

保持模型、接口和其他参数不变，改成 `--selection similarity` 可复测普通向量版本。
混合模式不会额外运行一组普通向量候选的聊天请求。
可用 `--hybrid-fetch-k 50 --rrf-k 60` 调整候选数和融合常数，候选数必须不小于最终 K。
MMR 和混合检索是独立实验模式，本次不叠加使用。

## 输出与诊断

主报告只显示三档目录的工具选择命中率和平均输入 token，不检查参数。
接口失败显示有效题数及失败次数，失败请求不当作工具选错，也不当作0 token。
完整逐题记录保存在构建日志目录的 `evaluation_details.json`，不挤进主报告。
其中保留原始向量排名、关键词排名/分数、是否进入任一路候选池以及最终工具列表。
`relevance_score` 仍是原始余弦相似度，不是融合分数。

新增离线测试验证倒排增删改、标识匹配、中文词语对应、融合去重、关键词补回候选、
无关键词命中时的行为、索引重载和查询缓存。离线通过不能证明真实 API 下命中率提高，
需要用上述命令实测。
