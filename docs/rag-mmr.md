# MMR 工具筛选与漏工具诊断

MMR 在候选选择时同时考虑“与问题相关”和“与已选工具不过于重复”，用于实验减少相似工具挤占位置。它不识别用户有几个需求，也不保证一定提高完整召回率。

## 运行过程

```text
原问题 → 一次向量化 → 全量余弦评分 → 阈值过滤 → 前30个候选
                                                       ↓
                                       MMR逐次挑选，最终最多10个
```

工具之间的相似度使用索引中已有向量，本地计算；不增加拆分模型或查询向量请求。查询缓存行为沿用原实现。

- 默认仍是普通相似度排序，显式开启 MMR 后生效。
- 候选池默认上限 30，最终数量由 `top_k` / `--k` 控制；候选池必须不小于最终上限。
- 相关性权重默认 0.7，仅作为实验起点；越接近 1 越重视相关性，等于 1 时退化为普通排序。
- 第一个工具取相关性最高的候选，之后最大化 `lambda * 问题相关性 - (1-lambda) * 与已选工具的最大相似度`。
- 原始余弦阈值在 MMR 前生效，返回的分数仍然是原始余弦分数。所有工具低于阈值时沿用现有“保留最佳工具”行为。
- 普通排序同分时按工具名排序；MMR 同分时沿用候选池顺序，使结果稳定。
- 空、零、维度错误及非有限工具向量不参与搜索；非有效问题向量返回空结果。

## 先只测召回，不调用聊天模型

在 Linux / WSL 设置好 `DASHSCOPE_API_KEY`（Embedding 密钥），运行：

```bash
python3 tests/rag_effectiveness/run.py --retrieval-only --selection mmr --k 10 --mmr-fetch-k 30 --mmr-lambda 0.7
```

这会评测同一批 80 题和 50/100/300 三档目录，同时计算“普通排序选10个”和“MMR选10个”的完整召回。两种方法复用相同问题、目录和缓存的查询向量，普通排序对照不增加 Embedding 请求。

输出仍为 `tests/rag_effectiveness/results/live-日期-编号/report.md`，包括：

1. 两种方法分别把多少道题的必需工具给齐，多工具题单独列出。
2. 平均实际候选数量；即使上限相同，阈值可能使实际数量不足 10。
3. 首次查询与缓存命中时的耗时。开启诊断的首次查询包含额外的本地完整排名计算，不能直接当作未开启诊断的生产耗时。
4. 漏工具原因汇总和逐题表：问题、正确工具、原始分数、原始排名及未选中的阶段原因。

仅检索模式不会生成“最终调用正确率”和“聊天输入 token”结论；缺少 Embedding 密钥返回 77，不能当作通过。

## 再测模型选择和输入量

在原有在线命令后加上 MMR 参数，保留自己的模型、对话地址和密钥环境变量配置，例如：

```bash
python3 tests/rag_effectiveness/run.py --live --selection mmr --k 10 --mmr-fetch-k 30 --mmr-lambda 0.7 --repeats 3
```

这个模式比较“全量工具”和“MMR筛选工具”的模型调用，同时展示普通排序与 MMR 的检索召回对照。它不运行普通排序候选的聊天模型组，因此不能据此直接声称 MMR 的模型调用正确率高于普通筛选；需要时另跑 `--selection similarity` 保持其他条件一致。

工具定义、题目标签、最终模型提示词均未因 MMR 修改。小于等于最终 K 的目录沿用评测后端原有“返回全部工具”分支，不受阈值或 MMR 筛选影响。

## 漏工具原因怎么看

| 报告中的原因 | 含义 |
|---|---|
| 相似度低于阈值 | 正确工具没有通过原始相似度过滤 |
| 排名超过候选池上限 | 通过阈值，但没有进入 MMR 的前30个候选 |
| 进入候选池，但 MMR 未选入 | 工具已经可供 MMR 选择，但没有进入最终10个 |
| 通过阈值，但被数量限制截断 | 普通排序中没有进入最终 K 个 |
| 没有有效向量记录 | 诊断没有发现该工具的有效向量，正常效果评测不应出现，需要排查数据或索引 |

同一工具可能既低于阈值又排名靠后，报告优先显示阈值原因，同时保留分数和排名。这些是直接筛选原因，不能证明模型为什么给出较低相似度。

“原因汇总”按遗漏工具次数统计，一道题缺两项工具会计两次；“完整召回”按题统计，只要少一个必需工具，这道题就不算给齐。正确工具标签只在 Python 评分和诊断时使用，不提供给检索器。

MMR 不能补回候选池之外的工具，过强的去重复惩罚也可能挤掉用户确实需要的相似工具。先观察真实效果，再决定是否改变默认模式。

## C++ 接入

```cpp
MCPAgentConfig config;
config.rag_config.enabled = true;
config.rag_config.top_k = 10;
config.rag_config.enable_mmr = true;
config.rag_config.mmr_fetch_k = 30;
config.rag_config.mmr_lambda = 0.7f;
```

配置解析器支持 `--enable-rag --rag-mmr --rag-top-k 10 --rag-mmr-fetch-k 30 --rag-mmr-lambda 0.7`。检索库自身也支持 `RetrieverConfig::mmr`，并可针对一次查询覆盖选择方式，复用索引和缓存。

## 离线验证

```bash
cmake -S . -B build -DBUILD_MCP_EXAMPLES=OFF
cmake --build build --target test_rag_mmr -j2
ctest --test-dir build -R rag_mmr --output-on-failure
python3 tests/rag_effectiveness/run.py --self-test
```

可控向量测试覆盖相关性与去重复权衡、候选池和最终数量限制、阈值保底、同分稳定性及非法参数。模拟接口测试覆盖真实 C++ 检索、诊断排名、查询缓存、两种报告流程及“仅检索不请求聊天”。离线通过只证明实现行为符合测试，不是线上准确率数据。
